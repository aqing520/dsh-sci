# 研究决策与计划提交恢复

本轮范围是 W10/W13 的决策一致性和重新规划恢复，不代表真实科研闭环或发布验收完成。

## 决策绑定

- 新评估由内核绑定当前 `planId`；显式提交旧/其他计划 ID 会被拒绝。指定任务时必须是当前计划的评估或自定义任务；自动决策仍要求完成评估任务。完成评估任务的产物也必须属于同一计划。
- 自动 bridge 在接受请求时固定计划和任务归属，排队后不会把旧评估重新归到新计划。
- 旧版无计划绑定的评估保留可读；当前计划没有评估时只产生待审决策，即使历史计划复用了相同任务 ID。
- 决策保存评估 ID、完整评估内容摘要、上下文摘要、预算余量、迭代边界、停止规则及生成的新计划 ID。
- 上下文包含项目、完整计划、所选评估、冲突及预算限额。模型请求计数不参与上下文摘要，以允许重新规划自身正常计量；提交前另行检查预算耗尽。
- 评估任务未完成、跳过、统计方法要求审阅、未解决记忆冲突、项目暂停或缺预算时不能自动修订或作最终停止决定。
- 预算耗尽只暂停项目并记录待审，不能变为研究完成。重复读取同一决策复用记录和事件。

当前停止规则仍是通用控制流规则；主案例的预注册主指标、适用性、引用支持性和科研结论需独立验收。

## 重新规划提交

1. 在项目写入队列中读取项目与完整计划快照，恢复先前接受但未完成的结果/计划提交。
2. 在锁外调用规划器，允许模型预算预留取得项目锁。
3. 回到项目锁中比较项目、完整计划和决策上下文；暂停、新评估、任务编辑、冲突或预算限额变化使旧规划失效。
4. 新计划继承原迭代上限并提升版本。初次规划失败、没有旧计划的显式重试保持迭代计数，并保持暂停，等待用户恢复。
5. 先持久化 `plan-commits/<commitId>.json` 的 `prepared` 日志，再保存新计划、旧计划 superseded 状态、项目/索引、决策和固定 ID 的事件，清除旧 active context，最后标为 `committed`。
6. 日志已接受后发生中断，启动或下次串行操作按日志重放，不调用模型、不重新生成计划和事件 ID。接受日志之前的失败不产生新计划；显式重试会重新规划。

手动 `iterate()` 和自动决策共用提交日志与评估审阅门槛。普通 `replan()` 也使用完整计划摘要检查与日志，保留人工修复失败计划的入口。

## 边界与验证

项目队列和决策合并在同一桌面进程的不同 Repository/Orchestrator 实例间共享；这不提供多个独立桌面进程对同一目录写入的分布式锁。启动恢复函数须在独占启动期间调用，Repository 直接写入接口不替代内核队列。

`protocolReviewRequired` 是读取旧数据时计算的兼容性视图，比较计划持久状态时忽略该派生字段；底层任务协议、内容和状态仍参与摘要。

损坏内容、错误项目/计划绑定、错误日志文件名或恢复目标已被修改时拒绝恢复，不跳过日志或重置科研状态。日志使用现有元数据加密机制，未新增磁盘断电/fsync 保证。

行为证据见 `test/research-decision.test.ts`：跨实例并发、锁外预算计量、过期状态、旧评估隔离、审阅与预算门槛、决策事件幂等、无计划失败恢复、明文/加密写入前后故障及真实子进程退出恢复。测试使用合成研究对象，不修改真实案例，不证明研究结果正确。
